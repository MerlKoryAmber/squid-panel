## Сегодня (08.09) — LinuxToMBProxy / HIER_DIRECT

### Симптом (прод conf, анализ по paste + access.log)
- Клиент `172.22.10.25` (`LinuxToMBProxy`), `USER -`.
- Без `http_access allow` выше auth → `407` / `HIER_NONE`.
- С allow → `TCP_MISS/503` + **`HIER_DIRECT`** (не MB), хотя cascade: `never_direct allow LinuxToMBProxy` + peer allow.
- AD-группа `ad_proxy_mb_policy` на тот же MB **работала**.

### Причина (доки/исходники Squid, не «тренировка» на проде)
В `never_direct` checklist правило **`allow ad_proxy_mb_policy` (`proxy_auth`)** стояло **выше** src-правил.  
Для неаутентифицированного клиента → `ACCESS_AUTH_REQUIRED` → Squid **не оценивает** нижестоящие `never_direct` (в т.ч. `LinuxToMBProxy`) → `DIRECT_MAYBE` → **HIER_DIRECT**.  
См. `peer_select.cc` WARNING: *Username ACLs are not reliable here*; [HierarchyControl](https://wiki.squid-cache.org/KnowledgeBase/HierarchyControl).

Второй peer `MBhproxy-IP` без PASSTHRU **не лечил** DIRECT (проверено на проде до фикса) — корень был порядок never_direct.

Панель **не даёт** вручную крутить порядок never_direct (эмит из каскада/БД).

### Фикс (git `8c9eaae`)
`SquidConfigBuilder::orderedRoutingRules()`:
1. `never_direct` **без** proxy_auth  
2. `always_direct`  
3. `never_direct` **с** proxy_auth  

Тесты: `tests/squid_fragments_cli.php`, `tests/prod_conf_never_direct_cli.php` + fixture `tests/fixtures/prod_cascade_linux_mb.conf`.  
Лаба: PASS + `squid -k parse` на сгенерированном tmp; live lab conf/db **не** переписывали этим прогоном.
